# Architecture

InsightOS is a **framework**, not an application. The application in `apps/web` is a
consumer of the framework, and it is deliberately the least interesting part of the
repository: everything that constitutes analytical judgement lives in
`packages/analytics-core`, is importable on its own, and is covered by tests.

## Layering

```
packages/analytics-core/insightos/
  types.py          value objects + to_jsonable(); no engine imports
  statistics/       hand-written inference: t-tests, Mann-Whitney, chi-square,
                    Theil-Sen, STL-free seasonal decomposition, MAD z-scores,
                    Benjamini-Hochberg FDR control
  profiling/        schema, type inference, key detection, cardinality
  quality/          six weighted dimensions -> a single 0-100 score
  kpi/              role assignment -> domain detection -> KPI registry -> engine
  anomaly/          point anomalies, level shifts, severity fusion
  forecast/         damped-trend projection with prediction intervals
  root_cause/       segment attribution and the explainable cause tree
  recommendation/   deterministic rules over engine output
  narrative/        deterministic sentence construction (+ optional LLM polish)
  visualization/    ChartSpec builders
  reporting/        executive report assembly and markdown rendering
  io/               csv / json / parquet / dataframe loaders
  demo/             synthetic generators with planted, recoverable ground truth
  pipeline.py       the only orchestrator
  cli.py            insightos analyse | demo build
```

The dependency direction is strictly downward. `statistics/` imports nothing from
InsightOS except `types`. `pipeline.py` imports everything and is imported by nothing.
Any module can be lifted into another codebase by copying its directory and `types.py`.

## Data flow

```
        dataset (csv/json/parquet/DataFrame)
                     |
                 io/loaders
                     |
              profiling  ->  TableSchema, ColumnProfile[]
                     |
               quality   ->  QualityReport (score, grade, dimensions)
                     |
             kpi/roles   ->  RoleMap   (metric / dimension / time / identifier)
                     |
            kpi/domain   ->  DomainDetection (domain, confidence, signals)
                     |
            kpi/engine   ->  KpiResult[]  (value, delta, favourability)
                     |
        +------------+-------------+--------------+
        |            |             |              |
     anomaly     forecast      root_cause     visualization
        |            |             |              |
        +------------+-------------+--------------+
                     |
             recommendation  ->  Recommendation[] (impact x confidence x urgency)
                     |
                narrative   ->  Narrative (headline + evidence bullets)
                     |
                reporting   ->  ExecutiveReport -> markdown
                     |
                AnalysisResult -> to_jsonable() -> static JSON
```

## The chart contract

`ChartSpec.__post_init__` raises if `narrative is None`. This single line is the
mechanism behind the project's central claim: **a chart cannot exist without an
explanation.** There is no code path that produces a renderable chart and leaves the
insight panel empty, because the type system refuses to construct one.

## Why the demo JSON is not committed

`apps/web/public/demo/*.json` is `.gitignore`d and regenerated by the Pages workflow on
every deploy. A committed fixture would let the published figures drift away from the
engine that supposedly produced them, and every number on the site would become
unverifiable. Regenerating at deploy time makes the live demo a continuously running
integration test of the engine.

## Runtime topology

* **GitHub Pages (default)** - the Next.js app is statically exported and reads
  pre-computed JSON. No server, no database, fully functional.
* **Docker Compose (full stack)** - FastAPI (`apps/api`) exposes the same pipeline over
  HTTP for real uploads; nginx serves the web build; the contract returned by the API is
  byte-compatible with the static JSON, so the frontend does not branch on mode.

## Testing

`tests/` covers the statistics primitives against closed-form expectations, the
root-cause engine against **planted** ground truth in the synthetic generators, and the
pipeline contract (every chart has a narrative headline, every recommendation cites
evidence). The test suite found three genuine engine bugs before release; they are
documented in the root `README.md`.
